# 注文から決済までを進める常駐市場サービス

`oclob-market-worker` は、法人側から届いた受付証明を保存し、注文の順序確定、MPCによる秘密照合、共同の証明作成、zkPI、DeFMIの正本台帳への決済を進める。固定の売り手・買い手ファイルを読み込む実演用プログラムとは別の実行経路である。

**検証状況：R14の最初の試験と、検査を追加した最終ソースでの通し試験がSoftbankで合格。3注文、2件の実決済、合計9,030円、14回のノード別確定確認と実プロセスの停止・復旧を確認した。116件のRustテスト、整形、警告を許さない静的検査も合格。製品としての完成を意味しない。**

## 今回見つかった問題

- 価格優先：従来のMPC回路は渡された注文位置の順に消化していた。価格が逆順の入力でも価格優先になるよう、秘密の割当計算を追加した。通し試験で差を確認済み。
- 受付段階の暗号文検査：最初の実装では、署名は確認するが、暗号文の外側にある注文識別子と長さの確認が決済時まで遅れていた。署名した本人が不整合な包みを送ると後続処理を止められるため、受付時に確認するよう修正した。回帰試験で拒否を確認済み。暗号文内部の不正まで、復号せずに全て検出できるとするものではない。
- 完了ログ：未約定の処理にも「正本で確定したラウンド」と読める英語ログを出していた。順序付きの照合処理を終えたという表現へ修正した。未約定時に決済が起きたとは表示しない。

## どこに何を置くか

```mermaid
flowchart LR
  C["法人の注文受付\n署名済み注文・資金の確保"] --> W["法人の常駐処理\n暗号化キュー"]
  W --> N["7つのMPCノード\n各ノードが注文の一部を保持"]
  W --> M["市場の常駐サービス\n受付証明・暗号化された決済権限"]
  M --> N
  N --> P["秘密照合・共同証明・zkPI"]
  P --> D["DeFMI\n正本台帳で資金と証券を同時に更新"]
  D --> F["各MPCノードが決済の確定を確認"]
  F --> M
```

法人の注文原文、本人確認資格、注文用の署名鍵、資産の秘密情報は法人側に置く。市場サービスへ送るのは、7ノードの受付証明と、一定数のノードが協力しなければ開けない決済権限である。この組を元の注文用鍵で署名する。市場側は接続証明書、注文用署名、7つの受領証を確認してから保存する。

`market.json` には接続先、接続証明書の要約値、参加法人の許可リスト、取引する2資産、保存先を設定する。暗号化記録の鍵は別ファイルに置く。接続先や資産を、既存の記録を残したまま別の値へ差し替えることは拒否する。

市場サービスは元の平文注文を持たない。ただし、接続した法人や通信時刻まで隠す実装ではない。法人の接続情報と注文との結び付きを隠すには、別途匿名化された通信経路などが必要になる。

## 保存と再開

市場の記録は、固定版DeFMIの暗号化記録部品を再利用する。同じ保存先を進める市場処理はOSのロックで一つに制限する。通信の受付処理は別スレッドで動き、計算中も新しい受領証を保存できる。

1. 受付証明と暗号化された決済権限を保存してから、法人へ受付応答を返す。
2. 受付順に次の注文を選び、順序証明と計算計画を保存する。
3. MPCの実際の結果とノードの署名を保存する。
4. 約定があれば、共同証明と署名済みの決済指図を保存してからDeFMIへ送る。
5. DeFMIの確定結果を各ノードが確認した後に、秘密の残高状態と市場の進捗を更新する。

同じ受付証明の再送には同じ受付番号を返す。同じ注文識別子で内容が違う場合は拒否する。決済指図を保存した後の再開では、保存した同一指図を使う。決済したか不明だからといって新しい指図へ置き換えない。

## 価格優先をどこで守るか

市場側は秘密の価格を使って板を並べ替えない。MPCの中で、各注文より価格が有利な注文の残量を数え、買い手・売り手の注文量を価格優先で割り当てる。同値の場合は先に受け付けた注文を優先する。証明と決済権限が参照する元の注文位置は変更しない。

通し試験では、101円の売り60単位、100円の売り60単位の順に受け付けた後、101円までの買い90単位を入れる。期待する割当は100円で60単位、101円で30単位、合計9,030円である。受付順のまま消化した場合の9,060円とは区別できる。

## 起動と確認

初回だけ、実験環境で作成した設定と鍵を使って記録を初期化する。

```sh
oclob-market-worker --initialize
oclob-market-worker
```

初期化を通常の起動へ混ぜない。記録がない、壊れている、鍵や対象デプロイが違う場合は停止する。記録の消失を「空の板」と見なさない。

法人側では `OCLOB_MARKET_CONFIG=/public/market.json` を設定する。`maker-worker` と `taker-worker` は7ノードへの配送が終わると市場へ受領証を送り、市場の受付応答を保存する。市場が停止していれば元の受領証を保持して再試行する。既存の法人向け受付済み表示は、引き続き決済済みを意味しない。

```sh
oclob-market-worker --status
oclob-market-worker --wait-rounds 3
```

これらは進捗を読むだけで、売り手や買い手を選んだり決済を実行したりしない。実験用の `--acceptance` も結果の検査専用である。

通し試験はMac上でビルドせず、以下のコマンドからSoftbankへ転送して実行する。

```sh
make remote-native-market-e2e REMOTE_TEST_HOST=softbank-l40s \
  REMOTE_TEST_SSH_OPTIONS='-o BatchMode=yes -o ProxyJump=none'
```

## まだ保証しないこと

- 今回は1台のホストに分離コンテナを置く機能確認であり、別事業者・広域ネットワークでの安全性や性能の確認ではない。
- 1回の計算に入れる既存注文は8件まで。上限を超える板を黙って切り捨てず、処理を止める。
- 保存する処理記録にも8,192件の上限を置く。注文数ではなく、各注文の途中段階も含めた件数である。長期運転向けの記録整理や退避は未実装。
- 取消、未約定注文の期限切れ、資産の自動解放までを常駐処理へ統合する作業は残る。
- 証明作成の途中、計画の期限切れ、他の処理による台帳更新など、全ての中断位置からの無人復旧は未確認である。
- この処理を認証付きAPIと画面へ接続する作業は別途必要であり、既存の画面を新経路で検証したとは扱わない。
- 新経路のMPCによる価格帯別の集計と、決済確定後の読み取り専用TLS配信は[公開板の通し試験](PUBLIC_DEPTH_JA.md)で確認した。[読み取り専用HTTP API](PUBLIC_BOOK_HTTP.md)も追加したが、取引APIとReact Flow画面への接続は残る。従来のデモを、新しい常駐経路の画面の実証へ流用しない。
- 回路の内容と要約値を変更したため、旧回路で未完了の注文や計算を残した環境への無停止入替えは未検証である。今回の試験は新しい分離環境で行う。
- 複数ホストからの同時運営、外部書込み、鍵の保護・更新、保存領域全体の巻き戻し対策は、単一ファイルのロックや暗号化だけでは解決しない。

# OCLOBが守るもの・守らないもの

## 1. 想定する相手

OCLOBは、次の参加者が自分の利益のために動く可能性を考えます。

- 市場運営者または受付順ノードが、注文を先に見て順番を変えようとする。
- MPCノードがshareを盗む、違う計算をする、結果が不利なときだけ停止する。
- 注文者が同じ資金・在庫を複数注文へ使う、結果を見て決済を拒否する、再送する。
- DeKYX資格を別市場や別期間へ流用する。
- DeFMIへ古いroot、別の市場、別の資産、改変したzkPIを送る。
- 外部観測者が公開板、約定、通信量、時刻から注文を推測する。

## 2. 信頼の置き方

### 2.1 MPC

- ノード数: 7。
- 秘密保持の前提: 最大2台まで不正。
- 復元に必要な台数: 3。
- 現在使う `malicious-shamir` 実行の可用性: 標準構成では7台すべての応答が必要。

「3台で秘密を復元できる」と「3台だけで処理を続けられる」は同じではありません。前者は秘密分散の閾値、後者は実行プロトコルの可用性です。

### 2.2 受付順

- 7台中5台が同じ受付文へ署名する。
- 最大2台の二重投票を想定する。
- 二つの競合する5票証明は作れないことを狙う。

ネットワーク上の絶対的な先着を保証するものではありません。クライアントが複数ノードへ同時送信し、各ノードの署名付き受領時刻を残すことで、検閲や不自然な遅延を後から検出する設計が必要です。

### 2.3 決済

- 注文者は注文時に許容範囲を署名する。
- 3-of-7の決済認可が閾値zkPIを作る。
- DeFMIは資金と証券を同じ原子的遷移で処理する。
- zkPIの使い捨て番号を再利用できない。

## 3. 保証する性質

| 性質 | 意味 | 現在の証拠 |
|---|---|---|
| 内容を見てからの差込み耐性 | 受付順確定前に注文内容を知って前へ入れない | commitment先行、5-of-7連鎖証明、MPC回路 |
| 価格・時間優先 | 高い買い、低い売り、同価格では早い注文から処理 | Rust基準状態機械とMPC出力一致検査 |
| 枠超過拒否 | 同じ法人の同時注文合計が資金・在庫を超えない | DeKYX無効化値と正本予約 |
| 事後拒否防止 | 約定後に再署名を要求しない | 事前署名、閾値zkPI、0 post-match signatures |
| 原子的DvP | 資金だけ、証券だけを更新しない | DeFMI staged transitionとroot読戻し |
| 再実行拒否 | 同じ注文、予約、指図を二度使わない | commitment集合、request digest、nullifier |
| 安全な停止 | MPC障害時に平文経路へ落とさない | fail-closedエラーと暗号化耐久キュー |

## 4. 保証しない性質

- 価格帯別合計を公開する以上、板差分から残注文を推測できる場合があります。
- 約定価格と数量を公開する以上、大口注文の存在を推測できる場合があります。
- IPアドレス、接続時刻、再送間隔、パケット量を隠す匿名通信網は含みません。
- 3台以上のMPCノードが秘密shareを結託して復元する状況は守りません。
- 注文端末自体が侵害されている状況は守りません。
- 市場外の価格操作、相場操縦、見せ玉を暗号だけで判定しません。
- 全ノード停止やネットワーク分断でも必ず約定する可用性は保証しません。
- TEEを安全性の根拠には使いません。CPU製造者、remote attestation、マイクロアーキテクチャのサイドチャネルを信頼境界へ追加しない方針です。

## 5. 中央非開示経路の実装範囲

分散受入経路では、法人側が注文を7つへ分割し、各MPCノードの公開鍵で別々に暗号化して直接送ります。各ノードは自分宛ての暗号文だけを保存し、実行時に自分の分割値だけを開きます。調整役が受け取るのは注文の要約値、受付順証明、公開約定結果、ノード署名だけです。固定長通信により、注文値によるメッセージ長の違いも出しません。

この経路はOmenX上の7コンテナで受入済みですが、1台のホストと一つの管理境界を使っています。したがって、7社の独立運用やWAN耐性を証明するものではありません。また、ブラウザ用の単体デモは中央調整プロセスが `SecretOrder` を一時的に持つ従来経路です。

本番受入には次が必要です。

1. DeKYX資格とDeFMI予約を、注文署名・入力分割と暗号的に結合する。
2. 各運営者が自分のMPC鍵を生成し、他ノードの秘密鍵を含まない配布物を使う。
3. 7ノードを別管理主体・別host・別KMS/HSMで稼働させる。
4. WAN障害、選択的停止、古い状態への巻戻しを試験する。
5. ブラウザと公開APIを分散経路へ接続し、中央平文経路を無効化できるようにする。

この未充足を解消するまで、OCLOBを実資産市場へ投入しません。

## 6. 受入で必ず攻撃する項目

- 同じ受付番号への別commitment投票。
- 受付後のshare差替え、欠落、順序変更。
- 一つの注文で9件以上と約定しうる固定枠超過。
- 同じ法人が別ウォレットから同じ枠を超える同時注文。
- 期限直前の注文・取消競合。
- MPC 1台、2台、3台停止と、結果判明後だけの停止。
- 古いDeKYX epoch、別市場のpresentation、再利用nullifier。
- 古いDeFMI root、片legだけの更新、同一zkPI再送。
- サービス再起動後の暗号化キュー復元と順番保持。
- 運営者API、ログ、エラー文、画面に秘密値が出ないこと。
